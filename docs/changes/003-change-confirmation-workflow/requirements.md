# 产品需求：变更确认流程

## 背景与问题

原规则要求为新增需求、架构调整和跨模块任务建立任务文档，但没有定义统一的停止点和有效确认条件。Agent 因此可能在完成文档前后直接进入实现，使用户无法先审阅需求和技术方案。

任务级文档原本位于根目录的独立目录，与已经约定的 `README.md -> docs/` 文档入口不一致，且目录名无法准确覆盖需求、设计、任务账本和完成证据的完整生命周期。

## 已确认选择

- 任务级文档迁入 `docs/changes/<seq-num-name>`。
- 所有非纯文档改动和状态变更操作都必须经过确认门禁。
- 初始实现指令不算确认；确认必须发生在方案报告之后的后续消息中。
- 方案阶段文档不单独提交，确认后与实现一起提交。
- 本次新增 `003-change-confirmation-workflow` 记录治理过程。
- 保留 `be76f39` 中的应用入口，但明确追记未经确认便实施的偏差，不把保留视为追认。

## 验收标准

- `AGENTS.md` 明确定义适用范围、方案阶段、有效确认、重新确认条件、实施边界和纯文档例外。
- 文档入口形成 `AGENTS.md -> README.md -> docs/README.md -> docs/changes/**`。
- 001、002 的历史内容完整迁移，所有相对链接有效。
- 002 明确记录流程偏差和 `VER-001` 未完成状态。
- 旧任务目录和旧路径引用归零，不形成双轨。
- 本次只提交文档变更，不修改 Go 文件，不运行或宣称 Go 门禁，不 push。

## 非目标

- 不回退或修改 `cmd/app`。
- 不改变 Kernel、Database、CLI 或 Supervisor 的行为。
- 不为具体架构主题建立新的权威说明。
- 不把确认门禁扩写为项目管理系统或审批平台。
