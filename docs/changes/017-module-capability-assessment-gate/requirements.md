# 需求：应用模块能力评估门禁

## 1. 背景

当前规则已经覆盖第三方边界、资源所有权、取消、超时、停止和研究门禁；项目也已有能力清单、Kernel App 组件形态和 Todo 研究先例。但这些知识没有在当前应用模块开发入口中形成必答检查。用户只要求“新增应用模块”时，Agent 可能直接模仿 Todo，而不显式证明现有能力是否足够、是否需要新 Capability、资源由谁治理，以及当前生命周期契约是否适用。

本需求由 [R001](research/R001-current-module-capability-assessment/report.md) 支撑。

## 2. 目标

- 让新增模块研究在写目录、接口或源码前完成能力差距和生命周期适配性判定。
- 让“无需新增能力”也成为有证据的显式结论，而不是因未提及被默认接受。
- 让 `AGENTS.md` 保持通用，只声明何时必须进入项目指引，不复制 `go-scaffold2` 的 Kernel、目录、Reload 策略或任务清单。
- 让项目当前文档形成 `AGENTS.md -> README.md -> docs/README.md -> 应用模块开发指南 -> 能力/Kernel 专题` 的单轨导航。
- 当当前 Kernel 契约无法表达真实资源语义时，阻止 Agent 用近似接口或虚假生命周期继续实现。

## 3. 范围

### 3.1 包含

- `AGENTS.md` 的一条通用研究语境和项目文档导航规则。
- 当前项目应用模块开发权威指南及能力评估模板。
- 根 README、文档索引、模块目录说明、能力清单和 Kernel App 说明之间的导航。
- 新模块研究报告必须包含的能力、资源、配置、生命周期、契约适配和升级结论。
- 消息、邮件和搜索三个边界示例。
- 文档结构、链接、术语、状态和差异验证。

### 3.2 不包含

- 修改 Kernel、Host、Supervisor、composition 或应用模块源码。
- 新增消息、邮件、搜索、认证、调度等具体能力。
- 选择 NATS、Kafka、RabbitMQ、SMTP 服务、邮件 API、Meilisearch 或 Elasticsearch。
- 为所有语义判断建立自动代码生成、万能表单或新的运行时 Registry。
- 把项目特有架构细节复制进 `AGENTS.md`。

## 4. 核心需求

### AGT-001 通用 Agent 规则

`AGENTS.md` 只能说明通用触发语境：当任务新增应用/业务模块、通用能力或外部系统接入时，先按项目文档识别现有能力、依赖边界、资源所有权、生命周期和基础契约适配性；项目没有可验证路径或契约不适用时，停在研究/计划阶段。

该规则不得出现当前项目专属组件 API、目录清单、具体消息产品或 Reload 枚举。

### NAV-001 单轨入口

- 根 README 提供“扩展项目”入口。
- `docs/README.md` 把“应用模块开发”列为当前主题。
- 应用模块开发指南是能力评估流程的唯一当前权威。
- `internal/module/README.md` 只说明包职责和依赖方向，并链接指南。
- `pkg/README.md` 继续拥有当前/暂缓能力清单。
- `internal/kernel/app/README.md` 继续拥有组件 API、生命周期形态与接入步骤。

### CAP-001 必答能力清单

每个新增应用模块的研究必须列出真实用例需要的全部外部效果，并对每项给出以下结论之一：

- 复用现有 Capability；
- 模块内专属 Adapter，不形成进程共享底层能力；
- 新增跨模块或进程级 Capability；
- 当前证据不足，停止计划并继续研究。

### OWN-001 资源与运行 owner

涉及连接、Client、listener、订阅、goroutine、缓存、事务或后台任务时，必须定位构造、启动、就绪、运行、停止、等待和释放 owner。共享资源消费者不得获得未授权的 `Close` 权。

### LIFE-001 生命周期与配置分类

项目指南必须要求基于真实能力分别选择构造来源、输出形态、配置契约、运行生命周期和 Reload 策略，不得因为 API 已存在就机械增加空 Hook、Lease 或热重载。

### GAP-001 契约适配与升级

如果需求涉及当前未支持的生命周期、切换、依赖或一致性语义，研究必须明确标记“当前契约不适用”，说明缺口、最小替代路径和验证计划，并建立独立变更或 ADR。不得用 `KernelInstanceSwap`、`RestartRequired` 或模块 Participant 冒充未实现的保证。

### SEM-001 能力专项语义

消息、邮件、搜索等示例必须提示各自的业务与运行语义，但不得把示例固化成所有实现都必须使用 Kernel 的结论：

- 消息：ack、幂等、顺序、重试、死信、背压、断线恢复、排空；
- 邮件：接受与送达、模板、幂等、重试、队列和投递诊断；
- 搜索：查询模型、索引转换、一致性、补偿、重建和索引切换。

### GOV-001 研究交付格式

`docs/research/README.md` 应把能力评估加入新增模块/外部系统任务的研究要求。结论为“无新能力”时也必须保留已核对清单和证据。

## 5. 验收标准

1. 从 `AGENTS.md` 出发，读者能通过根 README 和 `docs/README.md` 到达唯一应用模块开发指南。
2. `AGENTS.md` 中没有 `go-scaffold2` 专属 Kernel API、目录布局或具体技术产品清单。
3. 指南能独立回答“是否需要新能力、谁治理资源、选择何种生命周期、契约是否适用”。
4. 指南引用当前 `pkg` 能力清单和 Kernel App 组件说明，不复制会漂移的完整枚举与 API 正文。
5. 新模块研究模板要求显式填写能力清单、资源 owner、配置/生命周期、契约适配和升级决定。
6. 消息、邮件、搜索示例均同时覆盖业务语义和资源语义，不预选供应商。
7. 历史 012 变更记录不再被描述为当前操作权威；当前事实与历史状态不冲突。
8. 所有链接有效，术语统一为应用模块、底层 Capability、Kernel App 组件和 composition root。
9. `git diff --check` 通过；纯文档任务不宣称 Go 测试证明文档语义正确。

## 6. 非功能约束

- 文档和规则以中文为主，标识符及协议名保留英文。
- 一个主题只有一个当前权威正文，其他位置只链接和说明自身职责。
- 必答表应允许按真实复杂度裁剪，不强迫每个模块拥有配置、CLI、HTTP、中间件或生命周期。
- 不把“多想一些”写成模糊要求；每项判断必须有可复核输出和停止条件。
