# 定时调度能力需求

## 1. 文档状态

- 变更编号：`037`
- 当前阶段：已确认并实施完成
- 实施状态：待用户确认
- 研究依据：[R001 当前能力盘点](research/R001-current-scheduling-capability-inventory/report.md)、[R002 主源调研](research/R002-scheduler-and-coordination-primary-sources/report.md)、[R003 单轨集成结论](research/R003-single-track-integration-synthesis/report.md)

本文件描述本次变更必须满足的需求，不代表当前代码已经具备这些能力。

## 2. 目标

在现有 Application Generation、Module Binding、Execution、Cache、Tracing、Health、Supervisor 和 Runtime 机制上补齐统一定时调度能力，使业务模块只声明：

1. 执行什么任务；
2. 何时触发；
3. 使用什么并发、执行权和故障策略。

调度能力负责触发时机、运行治理、并发控制和分布式执行权协调，不承载业务逻辑，不建立平行的生命周期、健康、运行状态、重试、幂等或执行记录体系。

## 3. 术语与语义

### 3.1 Schedule Binding

业务模块通过不可变的 Schedule Binding 声明任务。每个声明至少包含稳定 Task ID、触发方式、任务函数、并发约束、执行策略和协调策略。

Task ID 在同一应用内必须唯一，用于配置覆盖、诊断、日志、Tracing、执行记录和协调键派生。Task ID 不得包含实例地址、随机值或 Generation ID。

### 3.2 触发方式

- `cron`：按照指定时区的 cron 表达式计算执行周期。
- `fixedDelay`：一次运行结束后等待固定间隔，再触发下一次运行；不得退化为从上一次开始时刻计算的 fixed rate。

### 3.3 执行作用域

- `local`：每个应用实例按本地并发策略执行。
- `distributedSingleton`：同一任务在同一执行周期内只有持有有效分布式执行权的实例能够触发执行。

`distributedSingleton` 只约束调度执行权。业务副作用的幂等和最终一致性继续由现有 Execution 能力及业务资源自身的事务语义保证。

### 3.4 协调不可用策略

每个分布式任务必须显式声明协调能力不可用时的策略：

- `skip`：跳过当前不可安全判定的周期，并保留后续自动恢复能力。
- `pause`：暂停该任务并使调度健康状态进入不可就绪，依赖恢复后自动重新参与。
- `fail`：把持续或确定性故障升级到现有 Generation/Supervisor 失败路径。
- `local`：仅允许明确声明弱化语义的任务在协调不可用时按本地策略运行。

严格单实例任务不得选择 `local`，也不得由系统隐式回退为本地执行。

## 4. 功能需求

### FR-001 模块声明与统一装配

- 项目必须定义自有 Schedule Binding 契约，并通过现有 `module.Contribution` 显式贡献。
- `internal/composition` 必须统一聚合、校验并绑定任务。
- 业务模块不得导入底层调度库、Redis 客户端或协调实现，不得拿到底层 Scheduler/Locker 句柄。
- 禁止 `init`、包扫描、全局 Registry、反射发现和第二条隐式注册路径。
- 重复 Task ID、无效触发器或策略组合必须使候选 Generation 构建失败，旧 Generation 保持服务。

### FR-002 cron 触发

- 支持带秒和不带秒的受控 cron 语法，具体格式由集中配置和校验定义。
- 每个 cron 任务必须显式解析时区；缺省时区使用集中声明且有文档的默认值。
- 非法表达式、非法时区和无法表达的组合必须在 Prepare 阶段失败，不能延迟到首次触发时才暴露。
- 同一周期的稳定 occurrence key 必须由 Task ID 和计划触发时刻派生，不得使用实际开始时刻或随机值。

### FR-003 fixedDelay 触发

- 支持初始延迟和完成后固定延迟。
- 下一次触发时间必须从上一次运行完成时刻计算。
- 同一 Task ID 默认不得重叠运行；超时或取消完成后才能计算下一次触发。
- 分布式单实例 fixedDelay 必须由当前有效执行权持有者维护序列，不能让多个实例分别自由漂移后只在执行点抢锁。

### FR-004 并发与积压控制

- 每个任务可声明本地最大并发、重叠策略和触发拥塞策略。
- 必须存在全局有界并发保护，避免大量任务同时触发导致无限 goroutine 或无界队列。
- 默认策略必须集中、可校验、可观测，不得散落魔法值。
- 不允许以同一无业务语义的全局锁串行化所有任务；不同任务之间必须保持策略隔离。

### FR-005 分布式单实例执行权

- 协调契约必须由项目自有类型表达，Redis 类型不得泄漏到调用方。
- Redis 实现必须复用 Cache 能力已经拥有的连接和资源所有权，不得创建第二套 Redis 客户端或独立关闭路径。
- 执行权必须使用不可猜测 token，并通过原子比较 token 的方式续租和释放。
- 只有持有当前有效 token 的实例可触发严格单实例任务；续租失败、租约丢失或所有权不确定时必须立即关闭该任务的新执行准入，并取消可安全取消的在途运行。
- 租约 TTL、续租间隔、争抢退避和容错窗口必须集中校验；续租间隔必须显著小于 TTL。
- 协调恢复后，`skip` 和 `pause` 任务必须在有界退避后自动重新争取执行权，不要求重启应用。

### FR-006 生命周期与 Generation 切换

- 调度候选必须在 Application Generation Prepare 阶段完成构建和校验，但不能在 Commit 前触发业务任务。
- Commit 必须以单一、可审计的切换点开放新候选准入，并关闭旧候选准入。
- 同一进程内的旧、新 Generation 不得同时运行同一 Task ID。
- Retire/Abort/Stop 必须停止新触发、取消在途任务、等待有界收敛、释放执行权并汇总清理错误。
- 调度器终态故障必须进入现有 Generation monitor 和 Supervisor 路径，不建立第二套守护循环。

### FR-007 复用 Execution 治理

- 每次业务任务运行必须通过现有 `execution.Access`/`OperationExecutor`，复用超时、重试、幂等、执行记录和异步记录策略。
- 调度层负责生成稳定 Operation Key 和 occurrence key，不复制 Execution Store 或重试状态机。
- Execution 的错误包装必须保留 `errors.Is`/`errors.As` 可识别的原始原因；本变更涉及路径上已有的断链问题必须同步修复。
- 调度失败、协调失败和业务执行失败必须保持可区分类型，不能统一改写为无法判定的内部错误。

### FR-008 Tracing、日志、健康与诊断

- 后台任务必须通过现有 Telemetry 能力创建受控 span，并把 trace identity 传递给 Execution 记录。
- 不得创建第二套 tracer provider、logger 或 diagnostics registry。
- 生命周期、执行权状态转换、跳过/暂停/恢复、任务最终结果必须使用现有 Logger 契约记录结构化低敏日志。
- 日志不得记录业务参数、完整协调键、Redis 地址、凭据、任务返回内容或未经审查的原始错误文本。
- 现有运维诊断必须显示每个任务的触发类型、Generation、准入状态、最近计划/开始/完成时刻、执行权状态和稳定错误分类。
- `pause` 必须影响 readiness；`skip` 必须保持服务可用但暴露 degraded 诊断；`fail` 必须进入既有失败路径。

### FR-009 配置与热重载

- 调度器总开关、默认时区、全局并发、关闭超时和协调租约参数必须进入现有强类型配置与校验链。
- 任务业务身份和任务函数来自 Module Binding；环境相关覆盖由现有配置层按 Task ID 解析，不允许业务模块直接读取配置文件或环境变量。
- 配置变更必须通过现有 Generation 重建和 Commit/Retire 语义生效；候选失败时继续保留旧 Generation。
- 禁用任务必须显式可诊断，不能以“未注册”或静默忽略模拟禁用。

## 5. 非功能需求

### NFR-001 边界与依赖

- 第三方调度库和 go-redis 只存在于 Adapter/内部实现边界。
- 新包必须具有明确能力语义，禁止新增 `utils`、`helpers` 或万能容器。
- 不得引入循环依赖、反向依赖、全局可变状态或运行时 Service Locator。

### NFR-002 可测试性

- 时间、调度引擎和协调实现必须可替换为确定性测试实现。
- 并发、续租、失权、恢复和 Generation 切换测试不得依赖长时间 sleep 或偶然时序。
- 分布式测试必须覆盖至少两个逻辑实例争抢同一 Task ID 的场景。

### NFR-003 有界运行

- 所有 goroutine 都必须有 owner、取消信号和等待退出路径。
- 所有 Redis 调用、任务调用、关闭和等待都必须接收 context 或明确超时。
- 争抢、续租和恢复不得无限紧循环。

### NFR-004 单轨演进

- 新能力启用后只能保留一条模块注册、调度生命周期、协调和诊断路径。
- 不保留旧符号别名、兼容配置、平行 Adapter 或静默降级分支。
- 权威主题文档必须随实现同步，不能把本变更文档作为第二套现行使用说明。

## 6. 非目标

- 不在脚手架中实现具体业务定时任务或示例业务副作用。
- 不实现远程动态任务中心、可视化调度控制台、手工补跑 API、工作流编排或消息队列调度。
- 不实现多 Redis 节点 Redlock、共识系统或 fencing-aware 业务资源协议。
- 不承诺崩溃边界上的业务副作用 exactly-once；这需要业务幂等键、事务或 fencing token 被目标资源共同支持。
- 不新增数据库迁移或持久化执行记录后端；Execution Store 的外部持久化仍是独立后续能力。
- 不让 Cache 成为新的业务可见通用锁 API；协调能力通过专用 `coordination` 契约表达。

## 7. 验收标准

### AC-001 契约与装配

- 两个独立测试模块可各自贡献任务，composition 能按稳定 ID 聚合并拒绝冲突。
- 搜索确认业务模块没有直接导入底层调度库、go-redis 或内部 scheduler 类型。
- 任务在候选 Prepare 完成后、Commit 之前不会运行。

### AC-002 触发语义

- cron 表达式、时区、fixedDelay 完成后延迟和禁用配置均有确定性测试。
- fixedDelay 在执行时间长于 delay 时仍不重叠，下一次触发基于完成时刻。
- occurrence key 在同一计划周期和不同实例间稳定一致。

### AC-003 分布式唯一性与恢复

- 两个逻辑实例共享同一 Redis 测试端点时，严格任务在一个执行周期内只有一个实例获得执行权。
- token 不匹配的实例不能续租或释放他人租约。
- 协调不可用时，严格任务不会本地执行；`skip`、`pause`、`fail` 的状态和健康语义分别可验证。
- 协调恢复后，任务无需重启即可自动重新参与后续调度。
- 租约丢失后，旧 owner 立即停止新准入，且新 owner 接管前不存在进程内双 Generation 重叠。

### AC-004 运行治理

- 每次业务运行都经过 Execution，并产生与重试、结果和 trace identity 一致的执行记录。
- 每个任务并发和全局并发均有有界测试；没有无主 goroutine 或无限队列。
- 正常关闭、候选 Abort、热重载和 fatal failure 均进入现有生命周期/monitor/Supervisor 路径。

### AC-005 可观测性

- 后台任务 span、低敏结构化日志、调度诊断和 readiness/degraded 状态具有测试证据。
- 健康路径不产生 Warn/Error；正常取消和关停不被记录为 Error。
- 诊断不泄漏 Redis 地址、凭据、业务参数或完整协调键。

### AC-006 工程验证

- 所有新增/修改 Go 包通过格式化、静态检查、单元测试、竞态测试和仓库既有治理检查。
- `git diff --check` 通过，文档链接和配置示例可验证。
- 完整 Diff 只包含本变更确认过的任务文件，没有旧入口或失效文档残留。
