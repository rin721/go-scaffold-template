# R001：012 研究模式与当前任务门禁差距

## 1. 研究问题

012 的哪些研究学习机制可以稳定推广到所有仓库任务？现有“计划 -> 确认 -> 实施”流程在哪些地方不足以保证先研究、再计划？

## 2. 方法与范围

本研究只使用当前仓库主源：根 `AGENTS.md`、003 变更确认流程、012 研究索引、R021 metadata 与实施快照。研究同时检查当前 Git 分支和工作树，以确认本任务可以只修改文档并避开用户已有 `.agents/skills` 迁移与 `tmp/` 内容。

没有开展外部联网研究。问题是仓库自身治理规则与已有模式的提炼，当前主源已经足以回答；增加外部框架样本不会改变本任务结论。

## 3. 当前事实

### 3.1 003 与根规则

- 003 把流程定义为“事实分析 -> 建立任务文档 -> 待确认 -> 用户确认 -> 实施”，主要解决计划完成前直接修改实现的问题。
- 变更前的根规则要求从 README 和代码事实开始分析，但没有规定研究问题、档案位置、metadata、证据快照、适用性、时效、替代关系或研究门禁通过条件。
- 因此“事实分析”可以退化成不可检索的临时阅读，计划无法稳定证明它引用了哪些研究结论。

### 3.2 012 已验证的研究模式

- 012 每个研究主题固定包含 `metadata.yaml` 与 `report.md`；metadata 支持按问题、主题、关键词、场景、状态和时效检索。
- 新研究前先检索既有 metadata，命中后检查完整报告，不只使用摘要；证据不足时才新增记录。
- 证据绑定源码、文档、测试、版本、Commit 或日期快照，并记录适用、不适用、局限、review date 和 refresh trigger。
- 过时结论不删除，通过 `supersedes` 与 `superseded_by` 双向关系保留历史并维护单一当前结论。
- R021 明确区分“底层闭环已实施”和“真实业务用例仍未确认”，证明研究结论、实现事实与后续设计授权可以保持分离。

### 3.3 Git 范围

- 研究时当前分支为 `codex/012-business-module-architecture-plan`，本地提交领先同名远端一个提交；`git fetch origin` 成功。
- 工作树已有与本任务无关的 `.agents/skills` 删除/新增和未跟踪 `tmp/`；它们可以通过显式路径暂存与本任务文档可靠分离。

## 4. 推断与设计影响

### 4.1 可推广机制

以下机制不依赖 012 的业务模块主题，适合作为通用门禁：

- 先提出研究问题，再检索和补充证据；
- 使用 metadata 提供可检索摘要，使用 report 保存完整证据；
- 记录证据快照、适用性、局限、时效和刷新条件；
- 区分事实、推断、用户决策、目标设计和当前实现；
- 用替代关系保留历史，同时只维护一个当前结论；
- 证据足够形成范围和验收后才允许进入计划。

### 4.2 不应机械推广的部分

- 012 有 21 份研究记录，是任务复杂度导致的结果，不应把固定数量变成门禁。
- 每个任务不必联网；当前仓库主源能够回答的问题应直接用代码、配置、测试和 Git 事实解决。
- 研究档案不能替代用户确认、实现测试、权威主题文档或 ADR。

### 4.3 状态机调整

通用状态机应从“事实分析 -> 计划”改为具有明确停止点的“研究中 -> 研究门禁通过 -> 计划中”，随后纯文档任务可以直接实施，非纯文档任务进入“待确认 -> 已确认 -> 实施”。实施中新证据推翻前提时必须回退，而不是把未经研究的新范围直接并入当前代码修改。

## 5. 适用性与局限

本结论适用于本仓库的代码、配置、脚本、测试、文档治理和只读分析任务。只读分析无需为零变更创建目录，纯文档任务无需额外确认，但两者仍必须先研究。

本研究不判断未来研究工具、schema 自动校验器或项目管理平台选型，也不证明当前 Go 实现质量。历史 001-012 没有统一 `research/` 的部分不回填；新规则从 013 后续任务开始执行。

## 6. 研究门禁结论

关键问题已有当前仓库直接证据，事实与推断已经分离，未发现妨碍形成 013 计划的未知项。R001 状态为 `active`，013 可以进入计划阶段，并按纯文档例外完成规则与导航实施。
