# 开发设计：研究优先任务门禁

## 1. 状态机

```text
用户请求
  -> 研究中
     -> 检索既有 metadata
     -> 核验当前仓库与必要外部主源
     -> 形成 metadata.yaml + report.md
  -> 研究门禁通过
  -> 计划中
     -> requirements.md
     -> design.md
     -> tasks.md
  -> 判断交付类型
     -> 纯文档：按计划直接实施
     -> 非纯文档：待确认
        -> 用户在计划报告后的独立消息确认
        -> 已确认
        -> 按任务 ID 实施
  -> 验证并同步当前权威文档
  -> 提交并完成
```

研究证据不足时留在“研究中”。计划或实现发现新事实时，按影响回退：只补强不改变结论的证据可以更新研究记录；推翻前提时回到“研究中”；改变目标、接口、依赖、边界、迁移或副作用时回到“待确认”，重新提交计划报告。

## 2. 研究档案

每个新任务目录使用以下最小结构：

```text
docs/changes/<seq-num-name>/
├── README.md
├── research/
│   ├── README.md
│   └── R001-<semantic-name>/
│       ├── metadata.yaml
│       └── report.md
├── requirements.md
├── design.md
└── tasks.md
```

`metadata.yaml` 用于按问题、主题、关键词、场景、状态和时效检索；`report.md` 承载完整证据与推理。新任务先检索所有任务 metadata，再只打开命中的报告。旧记录被替代时保留历史，通过双向关系指向单一当前记录。

013 不在 `AGENTS.md` 复制完整 schema；根规则只声明强制语义，通用字段和记录方法由 [研究档案与报告](../../research/README.md) 统一说明。012 保持历史快照，不成为第二套现行流程文档。

## 3. 门禁判定

### 3.1 研究门禁通过

必须同时满足：

- 关键问题已经明确且有直接证据；
- 当前代码、配置、测试、入口和 Git 事实按任务相关性完成核验；
- 既有研究完成检索和时效判断；
- 事实、推断、目标设计和用户决策没有混写；
- 冲突证据、局限、剩余未知和刷新条件已经记录；
- 剩余未知不妨碍确定范围、验收和计划。

### 3.2 计划门禁通过

计划必须引用研究 ID，完整描述目标、范围、非目标、接口和文件影响、失败语义、验证、风险、稳定任务 ID 与依赖。非纯文档任务提交报告后停止，不修改实现、不暂存、不提交、不启动服务或执行外部写入。

### 3.3 实施门禁通过

研究门禁已通过、计划状态为“已确认”、确认发生在计划报告后的独立用户消息中，并且当前动作属于已确认任务 ID。任何条件缺失都不能以初始“直接实现”指令代替。

## 4. 例外边界

- 无副作用只读分析：执行研究并在回复中交付结论，不强制创建变更目录。
- 纯文档交付：仍先研究、再计划，但可以直接完成文档和提交，不要求第二次确认。
- 紧急修复：不绕过研究；可以缩小研究与计划篇幅，但必须保留故障事实、影响面、回滚或失败语义和确认边界。
- 外部研究：只在当前仓库证据无法回答选型、标准或上游语义时进行，不以研究数量作为门禁通过标准。
