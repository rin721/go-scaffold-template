# 研究范围与方法

## 研究问题

本报告回答以下问题：

1. 当前仓库如何选择、构造、交付、启动、停止和重新配置底层能力？
2. GitHub 上有代表性的 Go 脚手架如何完成相同职责？
3. 当前模型相对这些常见做法多解决了什么问题，又付出了什么成本？
4. 哪些做法值得吸收，哪些做法不应直接引入？

这里的“底层能力装配”包括：

- 配置加载、校验和默认值聚合；
- Logger、Database 等进程级资源的构造和所有权；
- 能力到业务构造函数的依赖传递；
- 进程启动、就绪、停止和失败清理；
- 配置变化时的实例替换语义；
- 装配图的显式程度、校验时机和可测试性。

以下内容不属于本次比较：业务分层优劣、HTTP/RPC 性能、ORM 选型、代码生成质量、部署平台和完整框架功能数量。

## 当前仓库取证方法

先从根 [README](../../../README.md) 进入，再沿真实调用链核对以下实现，而不是把说明文档直接当作结论：

- `cmd/app/main.go`：进程入口、基线 logger、配置源、composition 和 Host 调用链；
- `internal/kernel/composition/composition.go`：固定能力清单和稳定 Access 汇总；
- `internal/kernel/definition.go`：`Definition`、`Register`、构造与发布钩子；
- `internal/kernel/kernel.go`：启动、重载、提交和停止事务；
- `internal/kernel/handle.go`：`Access.Use`、租约计数、排空和代际切换；
- `internal/kernel/capability/logger` 与 `database`：两个已接入真实能力；
- `internal/kernel/host.go` 与 `pkg/supervisor`：进程级生命周期监督；
- 边界测试：禁止 `pkg -> internal`、Capability 自注册、反射和目录扫描。

本地事实以提交 `1cae643cd9f1734f216505b43d69aad6d8780386` 为研究基线。报告中的“当前实现”只指该快照及本次文档提交前未改变的源码。

## 外部样本选择

样本同时满足“有官方源码或模板可复核”和“代表一种常见装配范式”。GitHub Star 仅用于说明采用度量级，不作为架构质量评分。数字是 2026-08-11 的易变快照。

| 样本 | 采用度快照 | 代表范式 | 选择理由 |
| --- | ---: | --- | --- |
| go-zero | 33,256 | `ServiceContext` + 生成入口 | 高采用度微服务脚手架；依赖集中到服务上下文 |
| Kratos / kratos-layout | 25,860 / 490 | Wire 生成静态对象图 | 官方模板清晰展示 ProviderSet、生成装配和 cleanup |
| Uber Fx | 7,632 | 运行时 DI 容器 + Lifecycle | 运行时类型图和统一生命周期的代表实现 |
| go-clean-template | 7,648 | 纯构造函数手工装配 | 不依赖容器的显式 composition root 代表 |
| Google Wire | 14,415 | 编译期代码生成 DI | Kratos 模板使用的生成器；维护状态直接影响方案判断 |

## 对照维度

每个样本统一从以下维度比较：

1. composition root 位于哪里；
2. 依赖图由谁表达和校验；
3. 构造失败和 cleanup 如何传播；
4. 资源生命周期由谁拥有；
5. 业务代码拿到实例、接口还是聚合上下文；
6. 是否支持运行期配置变化及其一致性边界；
7. 是否依赖反射、代码生成或全局状态；
8. 扩展新能力所需修改面。

## 证据等级

- **代码事实**：可由本地源码或外部官方仓库文件直接确认。
- **官方说明**：来自项目 README 或官方维护文档。
- **报告推断**：基于前两类证据得出的影响判断，文中使用“意味着”“可能”“本报告判断”等措辞。

本报告不从 Star 数、宣传语或目录名称推导运行时能力。尤其是“未发现标准路径支持运行期事务替换”只限定于已检查的官方默认入口，不等价于证明整个生态绝无第三方方案。
