# 差异与取舍

## 差异一：对象图装配与资源代际管理不是同一问题

主流 DI 方案的核心问题是：“已知一组构造函数，如何得到应用根对象？”当前 Kernel 的核心问题是：“已知一组彼此独立的资源定义，配置改变时如何安全地替换正在服务的实例？”

因此不能只按代码量比较：

- Wire/Fx 可以自动解析 `repository -> use case -> handler -> server`，当前 Kernel 不做这件事。
- 当前 Kernel 可以在 Database 配置变化时等待进行中的 `Use` 结束、切换到新 Client 并清理旧 Client，Wire/Fx 的标准对象图生命周期不做这件事。
- 两类能力可以组合使用，但不应让一个机制假装解决另一个机制的问题。

## 差异二：直接依赖与间接 Access

主流脚手架把接口或实例直接注入对象字段，调用自然、类型清晰，也允许长事务或长连接在对象内部持续存在。实例需要替换时，通常通过进程重启获得新对象图。

当前 `Access.Use` 增加一次间接调用：

- 优点：Kernel 能精确知道旧代是否仍在使用；调用方无法关闭共享资源；实例替换对业务对象身份透明。
- 代价：Client 和派生资源不能逃逸回调；长事务会阻塞重载；多层业务代码可能被迫传播 callback；误用只有通过约束和测试才能发现。

本报告判断，只有“单次操作能在有界回调内完成”且“运行期替换价值明确”的能力适合该模型。Clock、ID 生成器、纯 Validator 等无资源能力通常无需为可替换性付出此成本。

## 差异三：显式顺序与依赖 DAG

当前 composition 的 Logger、Database 顺序同时承担启动和反向停止约定，但 Definition 没有声明依赖。这样做的收益是实现简单、行为确定、没有隐藏解析；限制是：

- 无法自动判断缺依赖和循环依赖；
- 无法根据配置变化计算依赖闭包；
- 新能力如果需要另一个可替换能力，会把 Build、租约和提交时序耦合在一起；
- 简单增加 `DependsOn []ID` 并不能自动解决跨能力候选引用和一致发布问题。

Wire/Fx 在对象图解析方面更成熟，但它们解析的是一次性构造图。若未来 Kernel 真正需要受托管能力依赖，必须先定义候选代如何引用同一事务中的其他候选、失败如何回滚、排空顺序和部分变化闭包，不能只复制 DI DAG 表面 API。

## 差异四：配置是构造输入还是事务协议

主流模板通常把 Config 传给构造函数；配置加载失败会阻止启动，变化后常通过进程重启应用。当前仓库进一步把配置段摘要、默认契约、候选 Snapshot 和 commit 结果纳入 Kernel 协议。

这带来两项少见优势：

1. 多个已变化能力在同一轮成功后统一发布，避免某个能力已换代而另一个仍失败的可见中间态。
2. cleanup 失败被标记为“已提交后失败”，调用方不会错误回滚已经公开的新 Snapshot。

相应成本是配置、生命周期和能力定义高度绑定。若把所有普通业务配置也纳入 Kernel，会让 Runtime 变成过宽的配置平台，因此应继续限制在受托管底层资源。

## 差异五：错误暴露时机

| 方案 | 典型错误暴露点 | 优势 | 局限 |
| --- | --- | --- | --- |
| 手工构造 | 编译、单元测试、启动 | Go 原生、定位直接 | 人工遗漏顺序或 cleanup |
| go-zero Context | 编译、构造/启动 | 简单直接 | 聚合对象的最小依赖难保证 |
| Wire | 生成期、编译期 | 缺 provider/歧义较早暴露 | 依赖生成工具；Wire 已归档 |
| Fx | `fx.New`、ValidateApp、启动 | 大图复用和替换灵活 | 错误不是原生编译错误，运行时认知成本高 |
| 当前 Kernel | Register、Start、Reload | 同时校验配置和资源就绪 | 不校验业务图，也不校验能力依赖图 |

## 差异六：扩展成本

在当前仓库新增受托管能力通常需要：

1. 保留或新增独立 `pkg` 能力契约；
2. 定义 Kernel typed Config、Defaults、Builder 和 Hooks；
3. 定义专用 Access，收敛资源所有权；
4. 增加 composition 登记、默认配置和可选 CLI contract；
5. 增加启动、失败、重载、排空、停止和边界测试；
6. 更新主题文档。

这个成本高于向 `ServiceContext` 加一个字段或向 Wire/Fx 加一个 provider。高成本只有在换代安全确实是产品需求时才合理；否则会把通用库适配成不必要的运行时组件。

## 当前模型的相对优势

- 没有反射、自注册、包扫描和全局容器；真实启用清单集中可见。
- `pkg` 与 Kernel 解耦，第三方实现和资源所有权被项目契约收敛。
- 配置候选失败继续使用旧代，适合数据库、日志 sink 等进程级资源。
- 多能力提交具有一致可见边界，错误区分提交前失败与提交后清理失败。
- 租约使 shutdown/reload 能等待真实使用者，而不是仅靠固定延迟。
- 基线 logger 在早期启动和 Logger Capability 失败期间仍然可用。

## 当前模型的相对短板

- 不构造业务对象图，随着业务进入仍需要另一个静态 composition root。
- `Capabilities` 若持续横向增加并整体下传，可能演变为 go-zero 风格的大上下文。
- `Use` 的不逃逸规则难以由 Go 类型系统完全证明，Database 派生对象尤其容易误用。
- 一个长租约会延长或阻塞重载；目前依赖超时终止事务，而不能强制回收调用方。
- 无 Capability DAG，因此“彼此独立”既是简化假设也是扩展上限。
- Definition、Access、composition 和测试的样板明显高于主流启动期装配。
- 当前真实接入只有 Logger、Database，尚不足以证明该模型适用于所有底层能力。

## 不应得出的错误结论

- 不能因为 Fx 有 Lifecycle 就认为它等价于当前配置事务。
- 不能因为 Wire 生成显式 Go 代码就认为它能自动处理运行期资源换代。
- 不能因为 go-zero 的 `ServiceContext` 简单就把 Kernel Handle 或所有能力整体暴露给业务。
- 不能因为当前 Kernel 支持重载就要求每个 `pkg` 能力都进入 Kernel。
- 不能把本报告建议的静态业务对象图、Profile 或诊断 Plan 写成当前已实现功能。
