# Go 脚手架底层能力装配架构对比

- 状态：已完成
- 研究日期：2026-08-11
- 当前仓库基线：`1cae643cd9f1734f216505b43d69aad6d8780386`

## 结论摘要

当前仓库不是另一种常规 DI 容器，而是把少量底层资源做成了**可在运行期按配置事务重建的 Capability Runtime**。它与 GitHub 主流 Go 脚手架最核心的区别，不在于“手工装配还是自动装配”，而在于被装配对象的生命周期模型：

- 主流脚手架通常在进程启动时构造一次静态对象图，随后由应用生命周期统一启动和停止；依赖以构造函数参数、生成代码、`ServiceContext` 或运行时容器传递。
- 当前仓库在启动前仍使用显式固定清单，但业务侧得到的不是当前资源实例，而是稳定 `Access`。Kernel 能在运行期间构造候选实例、阻止新租约、等待旧租约排空、统一发布新代实例并清理旧代。
- 因此，当前模型在无反射、依赖可见性、资源所有权、失败保留旧实例和多能力一致切换方面更强；代价是 `Use` 回调约束、能力必须彼此独立、组合样板较多，并且尚不具备主流 DI 方案提供的业务对象图解析、编译期缺依赖检查或模块复用机制。

研究结论不建议用 Fx、Wire 或 `ServiceContext` 整体替换 Kernel。更合适的目标是两条装配平面并存：

1. 只有确实需要运行期安全替换的底层资源进入 Kernel Capability 平面。
2. 业务 service、use case、handler、server 继续使用普通构造函数形成启动期静态对象图，并从 Capability Access 获得所需能力。

当前阶段保持手工显式装配即可。只有当业务对象图的规模和重复度出现可测量问题时，再单独评估代码生成或运行时 DI；Google Wire 已归档，不应在没有替代维护方案的情况下作为新增长期依赖。

## 主要差异

| 维度 | 当前仓库 | 主流默认路径 |
| --- | --- | --- |
| 核心模型 | 动态 Capability 代际管理 | 启动期静态对象图 |
| 选择方式 | composition 固定清单显式登记 | 手工构造、生成图、`ServiceContext` 或容器模块 |
| 依赖解析 | 不解析 DAG，能力彼此独立 | 由代码顺序、生成器或容器解析对象依赖 |
| 业务获得依赖 | typed `Access.Use` 租约 | 直接持有接口或实例 |
| 配置变化 | 候选构造、排空、原子发布、失败保留旧代 | 通常重启进程；默认装配路径不跨资源事务替换 |
| 生命周期 | Kernel + Supervisor；资源按登记顺序启动、反序停止 | App/Lifecycle/`defer` 管理启动与停止 |
| 图校验 | 注册期校验 ID/配置契约，测试守护边界 | 编译器、Wire 生成期、Fx 启动期或人工审阅 |
| 主要风险 | 回调逃逸、排空等待、动态语义复杂、无依赖图 | 聚合对象膨胀、隐藏运行时图、生成器维护或手工样板 |
