# 复杂度根因

## 1. 必要复杂度与非必要复杂度

评价当前架构不能只看文件数量。无感实例切换天然包含并发、资源所有权和失败恢复问题；删除状态机并不会让这些问题消失，只会把风险藏起来。

本报告把复杂度分成两类：

| 类型 | 内容 | 判断 |
| --- | --- | --- |
| 必要复杂度 | 租约计数、排空、候选构造、失败恢复、资源反向清理、错误链 | 只有选择 `KernelInstanceSwap` 的组件需要 |
| 必要复杂度 | 排他资源交接、切换后健康观察、回切、代际上限 | 目标语义要求，当前尚未实现 |
| 非必要认知成本 | 每个组件都先理解同一套最重协议 | 应由策略和框架入口屏蔽 |
| 非必要样板 | Definition、Access 适配、composition binding、聚合字段之间的机械搬运 | 可通过单一组件入口和明确约定收敛 |
| 非必要耦合 | 默认配置、CLI、实例换代必须一起出现 | 应改为可选小契约 |
| 非必要前置设计 | 在没有消费者时提前建立通用业务 DI、DAG、scope、运行时 Resolver | 应继续避免；底层组件只需要有序 typed 手动计划 |

## 2. 设计目标在迭代中发生了语义漂移

最初的“底层可替换”可以用依赖倒置完成：

```text
业务 -> 项目自有接口 <- 第三方 Adapter
```

后来它被扩大为：

```text
业务 -> 稳定 Access -> 运行期可替换实例 -> 多能力配置事务
```

后者不是前者的自然同义词，而是一项独立且更昂贵的运行能力。AI 分步设计时，每一步都可能局部合理：封装第三方类型、增加生命周期、增加配置监听、避免 Reload 中断、等待旧调用、支持失败回滚。问题是缺少一次整体回看，没有持续追问“所有能力都需要这些语义吗”。

结果是局部安全要求不断叠加，形成了比原始目标更强的系统。

## 3. 框架内核和扩展者 API 没有分层

Kernel 内部需要知道 generation、candidate、draining、commit 和 cleanup；组件作者只应回答：

- 如何构造和验证实例；
- 如何判断就绪和健康；
- 如何关闭资源；
- 底层库支持哪一种重载方式；
- 业务能拿到什么窄能力。

当前 Definition 已经隐藏了部分内部状态机，但仍把配置、默认值、构造、Hooks、Activation 一次性摆在组件作者面前。composition 又要求作者手工拆装 Registration 的 Access 和 Defaults。这让框架内部协议泄漏成了扩展开发流程。

## 4. “统一”被误解为“每项能力形状完全相同”

一个好用的统一框架应统一治理入口和错误语义，而不是强制所有能力拥有同样生命周期：

- Clock 和 ID Generator 通常没有资源，不需要 Start、Stop 或实例换代；
- Database 有连接池、Ping 和 Close，但能否双实例并存取决于连接容量和外部约束；
- Logger 可能通过稳定代理实现原子委托切换；
- HTTP Server 绑定端口，通常不能直接把两个完整 Server 同时 Start；
- 消息消费者可能受到 consumer group、ack 和单活语义限制。

用可选小契约表达差异，才能同时做到统一入口和不过度抽象。

## 5. 配置热重载被当成二元能力

“支持 Reload”不是一个布尔值。至少存在五种不同语义：底层原子重载、Kernel 双实例换代、组件专用交接、必须重启和忽略变化。

如果只有一个通用 Reload 开关，组件作者只能：

- 硬套通用双实例协议；
- 在 Hook 内偷偷做特殊处理；
- 或假装某项配置可以无感生效。

显式策略的价值不只在执行，也在诊断。运维人员应能知道某次变化将原地生效、创建新代、等待交接，还是要求重启。

## 6. 主流框架为什么看起来简单

主流方案通常选择较弱但足够常见的默认语义：启动时构造固定对象图，停止时反向释放。它们把替换实现留在下次启动，把运行中的配置变化限制在少量库自有能力内。

例如 Fx 的 `Provide`、Module 和 Lifecycle 主要解决构造函数解析、模块复用以及 OnStart/OnStop；它没有要求普通模块为每个依赖实现租约排空和两代实例观察。其他框架展示的业务对象装配方式只用于解释其默认职责较窄，不构成本项目当前业务层设计依据。

因此不能用它们入口代码短，推导出当前强换代协议也应只有几行。正确的借鉴方式是：

- 独立组件拥有直接可调用的构造入口；
- 生命周期契约保持小而明确；
- 框架特有胶水集中在组件边界；
- 只有选择高级能力时才暴露相应复杂度。

## 7. 复杂度收敛原则

后续设计应遵守：

1. **统一准入，分类治理**：底层能力统一进入 `kernel/app` 和 composition，再分别选择构造、出口、生命周期与 Reload Policy。
2. **单一开发入口**：组件作者从 `kernel/app/<name>` 的一个定义入口开始。
3. **策略显式**：不从方法名、nil hook 或目录位置推断重载语义。
4. **内部状态机不外泄**：业务只看到窄能力，组件只实现所选策略需要的契约。
5. **守住当前阶段**：只设计底层组件装配，不提前定义业务层对象图。
6. **失败语义真实**：不能无感换代就声明需要重启，不用停旧启新冒充原子切换。
7. **实现后再宣称**：观察期、健康回切和专用交接在代码落地前都必须标为目标设计。
