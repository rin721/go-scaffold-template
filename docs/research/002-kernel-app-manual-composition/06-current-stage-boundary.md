# 当前阶段边界

## 1. 本报告停在哪里

当前项目只研究和建设底层通用库、Kernel 应用组件、显式 composition、配置与生命周期治理。报告的交付终点是：

```text
pkg/<name>
    -> internal/kernel/app/<name>
    -> internal/kernel/composition/<name>.go
    -> Kernel / Host
    -> 项目自有能力契约或租约 Access
```

底层组件在这个终点应按自身声明被构建，并在适用时被启动、检查、重载、回滚和关闭。无资源能力不需要伪造生命周期；第三方实现、资源关闭权和 Kernel 私有 Handle 不得越过能力出口。

## 2. 当前明确未建设的内容

以下内容不属于本报告的目标设计、目录建议、伪代码或验收条件：

- HTTP/RPC 入站服务和路由；
- middleware、handler 和协议 DTO；
- service、use case 和业务事务编排；
- repository、持久化映射和领域查询；
- model、领域实体和值对象；
- 上述对象之间的构造顺序、依赖方向或目录布局；
- HTTP health endpoint 或其他对外管理协议；
- 完整业务纵切和消费者项目。

“Kernel 不负责构造这些对象”只是一条当前范围声明，不代表本报告已经决定它们未来必须使用手工构造、静态对象图、代码生成或其他装配方式。

## 3. 为什么不能提前设计

当前没有真实业务用例、协议、事务边界和资源使用方式。此时给出任何具体业务构造链都会产生三个误导：

1. 把示意链路误认为已经确认的项目分层；
2. 用假想消费者倒推底层 Access 形状，使通用能力承担尚不存在的需求；
3. 把本次“底层能力怎样手动装配”的问题扩大成业务框架设计。

因此，本阶段只要求能力出口可独立验证，不要求用占位 handler、service 或 repository 证明它能被消费。

## 4. 当前怎样验收能力出口

在没有业务层的情况下，底层组件仍然可以完整验收：

- `pkg` 契约测试验证第三方封装、配置、错误和资源所有权；
- 组件测试验证所声明的 Build、可选配置、可选生命周期和 Reload Policy；
- Direct 输出测试验证接口多态和稳定身份，Leased Access 测试验证租约、Context 取消、派生资源边界和关闭权限；
- Kernel 测试验证配置事务、实例切换、观察期、回切和清理；
- composition 测试验证显式启用清单、typed Binding/Input、零值/跨计划输入、重复 Component ID 和严格登记顺序；
- Host 测试验证 Kernel Participant、Watch Task 和进程关闭期间的资源回收。

这些测试都围绕底层组件本身，不需要创建业务目录或伪造业务调用。

## 5. 未来何时重新打开业务层设计

只有用户后续明确提出 HTTP、handler、service、repository、model 或具体业务场景建设时，才从真实需求重新分析：

- 业务边界和目录；
- 谁定义依赖契约；
- 底层能力接口或 Access 如何被消费；
- 长事务、流或会话是否适合租约模型；
- 上层长期服务怎样加入 Host；
- 是否需要手工构造、代码生成或其他装配方案。

届时应建立独立任务文档并等待确认。本报告不对这些答案设置默认值，也不把当前底层组件方案当成业务架构授权。
