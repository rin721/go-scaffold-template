# 提交当前任务改动

把一次开发任务中可明确归属的代码、测试、配置和配套文档提交为一个自洽的 Git commit。保护任务开始前已经存在的改动，并服从用户指令、仓库规则和更高优先级约束。

## 执行原则

- 只操作当前任务明确指定的一个 Git 仓库。发现嵌套仓库、submodule 或多个候选仓库时，先确定唯一边界。
- 只有当前用户指令或适用的仓库规则已授权创建 commit 时才执行 `git commit`。仅隐式触发本 skill 不扩大授权；授权不清楚时完成审阅和验证后请求确认。
- 只提交当前任务产生且完成任务所必需的改动，包括相应测试、配置、迁移和文档；不提交顺手修改或任务开始前的用户改动。
- 不使用 stash、clean、reset、checkout/restore 丢弃改动等方式整理工作树。不以删除、覆盖或隐藏既有改动换取整洁状态。
- 不自动 push、merge、rebase、amend、创建或切换分支、改写历史。只有用户对相应操作给出明确授权时才执行。
- 不使用 `--no-verify` 绕过 hooks，不创建空提交，不提交秘密或本应忽略的生成物。

## 1. 在修改前记录基线

进入目标仓库后立即执行并保留结果：

```text
git rev-parse --show-toplevel
git status --short --branch
git branch --show-current
git diff --stat
git diff --cached --stat
```

同时记录任务开始前已修改、已暂存和未跟踪的路径。后续维护一份本任务实际创建或修改的路径清单；不要只凭任务结束时的 `git status` 推断归属。

如果工作树在 skill 启用前已经发生修改，先依据对话、现有 diff 和文件时间等可靠证据重建基线。无法可靠区分时，把相关路径标记为归属不明，禁止擅自提交。

## 2. 完成任务并验证

先完成用户请求，再按仓库文档执行与改动风险匹配的格式化、生成、测试、静态检查和文档检查。最后至少执行：

```text
git diff --check
git status --short
```

验证命令失败时先判断是否由本任务引起。修复任务范围内的问题；如果必需验证仍失败，则停止提交并如实报告，除非用户明确要求创建带已知失败的检查点 commit。

不得为通过验证而修改或提交任务范围外的文件。不得把未执行的检查描述为通过。

## 3. 审阅并划定提交范围

逐项核对本任务路径的完整 diff，确认行为、测试、配置和文档相互一致。特别检查：

- 是否混入任务开始前已经存在的修改或未跟踪文件；
- 是否遗漏重命名、删除、测试、生成结果或契约文档；
- 是否出现凭据、Token、私钥、真实连接串、个人数据、大型二进制或调试产物；
- 是否存在与任务无关的格式化、依赖升级或批量重写。

遇到以下情况时采用对应策略：

- 路径完全由本任务创建或从干净基线修改：可以按路径暂存。
- 路径在任务前已有改动，但本任务未修改：保持原样，不暂存。
- 同一文件同时包含既有改动和本任务改动：只有在能可靠分离时才暂存本任务 hunks，并在暂存后逐行复核；无法可靠分离时停止并请求用户决定。
- 已有 staged 内容不属于本任务：不得取消暂存，也不得把它并入本次 commit；停止并请求用户处理或授权明确的隔离方案。

## 4. 精确暂存

对已确认归属的路径使用显式 pathspec：

```text
git add -- <task-path-1> <task-path-2>
```

不得使用 `git add .`、`git add -A`、`git commit -a` 或仓库级通配符。在混合修改文件中，使用可审阅的 patch/hunk 方式只暂存当前任务部分；应用到 index 前先检查 patch，应用后再次查看 cached diff。

暂存完成后必须执行：

```text
git diff --cached --check
git diff --cached --stat
git diff --cached
git status --short
```

把 cached diff 视为即将交付的最终制品。若其中出现任何无法归属于本任务的内容，停止提交并修正暂存范围；修正过程不得改变用户工作树内容。若暂存区为空，不创建 commit。

## 5. 生成提交信息

先读取仓库规则；如果仓库已有 `HEAD`，再读取最近提交标题：

```text
git log -10 --pretty=format:%s
```

遵循仓库既有语言、格式和 Conventional Commits 等约定；不存在约定时，使用简洁的祈使式标题，描述完成的一个逻辑结果。必要时在正文说明动机、关键约束或兼容性影响，不罗列文件名，不声称未完成的验证。

一个任务通常只创建一个 commit。只有用户或仓库规则明确要求拆分，且每个 commit 都能独立成立时才拆分。

## 6. 创建并核验 commit

再次确认已有提交授权后执行普通提交：

```text
git commit -m "<subject>"
```

若 hook 失败，保留其保护作用，调查并修复任务范围内的根因；不要绕过 hook。提交成功后核验：

```text
git show --stat --oneline --decorate HEAD
git status --short --branch
git diff --cached --exit-code
```

确认 `HEAD` 正是本任务 commit，index 没有本任务遗留，并且任务外改动仍原样保留。不要因为 commit 成功而自动 push。

## 交付报告

向用户简洁报告：

- commit 短哈希和完整标题；
- 提交包含的任务范围；
- 实际执行的验证及结果；
- 仍留在工作树或暂存区、未包含在 commit 中的既有或归属不明改动；
- 未执行项、已知失败和是否尚未 push。

如果没有创建 commit，明确说明阻塞原因和需要用户决定的事项，不用“已完成”掩盖未提交状态。
